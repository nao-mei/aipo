# Handover: maintaining the published site

This repository holds the **built, published site only**. The full source (build scripts, tests, content spec, review records) is kept separately in a private repository. This file tells you what you can safely do from here and what you need the full source for.

## What is in this repo

| Path | What it is |
|---|---|
| `index.html` | App shell and styles. Includes a "noindex" tag. |
| `app.js` | The interface and hash router. Contains the build stamp. |
| `logic.js` | Pure logic: spaced-review boxes, mastery and readiness, study plan, streak. |
| `mascot.js` | The robot artwork as shape data. |
| `sw.js` | Service worker (cache-first, offline). Contains the version stamp and the file list to precache. |
| `manifest.webmanifest` | Install metadata. Paths are relative so the site works under a sub-path. |
| `icons/` | App icons (generated from the robot artwork). |
| `content/` | All study content: `domains.js` plus one file per domain (`intro`, `po`, `frame`, `data`, `eval`, `hax`, `risk`, `ops`, `use`). |
| `.nojekyll` | Tells GitHub Pages to serve files as they are. |

Hosting: GitHub Pages, deploying from the `main` branch, root folder. The site address is the repo name; **do not rename the repo**, because learner progress is stored per web address.

## Safe edits made directly here

- **Fixing a typo or wording in content:** edit the relevant `content/<domain>.js` string. Keep the literal `\n` sequences inside lesson bodies and flashcard backs.
- After **any** edit, bump the version so phones pick up the change: change `VERSION` at the top of `sw.js` and `BUILD` in `app.js` to the same new value (for example `20270101.1`). If you skip this, installed copies keep the old cached files.
- Commit and push; Pages redeploys in a minute or two. Reopen the app twice on the phone to pick up the update.

## Edits that need the full source

- Adding or removing questions, lessons, domains, flashcards or scenarios (counts and the precache file list are generated by the build).
- Changing the readiness formula or study-plan rules (these have tests in the source repo).
- Regenerating icons or changing the artwork.
- Any re-review of content against sources (the spec, blueprint, source register and review records are in the source repo).

## Content format (for hand edits)

Each content file sets `window.AIPO.*`. Questions are `{ id, domain, type: "single"|"multi", pick, stem, options[], correct[], explanation, reviewed:false, scenario? }`. There must be exactly one entry in `why[id]` per option, in option order. Single-choice questions have 4 options; multi-select questions say "Choose TWO" or similar and `correct.length` must equal `pick`. Keep the correct answer spread across positions and avoid making it systematically the longest option.

## Content status and open items

- Every item is `reviewed:false`. Automated reviews were run per domain and their fixes applied, but a person has reviewed only some of the content.
- Known gaps: domains 1, 4, 6 and 8 have one scenario each (17 to 20% of their questions; the target was 25 to 30%). The Scrum.org Evidence-Based Management Guide and the Microsoft guidelines paper were not read from the originals; only concept names and counts are used. The local copy of the Google guidebook may be an older edition than the live one.
- **Re-review triggers:** NIST publishing a revised AI RMF or an updated Playbook (subcategory IDs and wording may change); a new edition of the Scrum Guide; any change to the Google guidebook or the Evidence-Based Management Guide.
- Tested on a phone by the owner and works well.

## Testing checklist after any change

1. Open the live site in a private window: home loads, no errors.
2. Open a lesson, answer a drill question (feedback and per-option explanations show), flip a flashcard.
3. Check dark mode and a narrow (360px) width: no sideways scrolling.
4. After bumping the version, confirm Settings shows the new build value.
5. Search the files for names that should never appear (employers, clients, individuals) before pushing.

## Privacy and hygiene rules

- No company or client names, no personal data, no real-person names anywhere in the app or content.
- Commits use the repository owner's GitHub no-reply address only.
- No network calls, analytics or external fonts or scripts.
